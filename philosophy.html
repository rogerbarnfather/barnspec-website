Philosophy

Why Barnspec works the way it does.

Barnspec is built on a few decisions. Each one is a refusal of something common in how software projects are run, and each shows in how the tool behaves.

If the software disappeared, the value shouldn’t #

Imagine every line of code, every package and every ticket disappeared overnight. If what is captured in Barnspec were good enough, a different team on different technology could rebuild the product, and it would do the same things for the same people for the same reasons. That is the test a story has to pass.

So a story never describes a screen, an interface or a table. It describes a real, ongoing need that a kind of person has. Everything else follows from keeping that permanent record apart from the disposable details of how it happens to be built today.

A story is a statement of value, not a task #

A story has three parts: a role (a kind of person), a goal (what they want to do) and a reward (why it matters to them). It is always told in the third person: “The guest wants to book a room, so they have somewhere to stay.” It is never “As a guest, I want…”. In the first person a story reads like a developer’s guess at a user’s diary entry. In the third person it reads like a fact about the business, true whether or not anyone has built it.

A story has no “closed” or “deleted” state once it is real. It is written, then refined with concrete Scenarios, then fulfilled by whatever team and code exist at the time. Fulfilled is not the end: the need doesn’t stop being true because someone met it.

Proof, not sign-off #

Nobody can mark a Scenario fulfilled. There is no confirm button and no override. A Scenario turns green only when a real run against the real software passes, and stays green only while the next run passes too. Finishing the tickets gets a Scenario to red, which means “claimed, not proven”. Green is reserved for evidence.

That is deliberately uncomfortable. A Scenario nobody has written the checks for can never go green, however finished the work feels. The discomfort is the signal working: a colour that said otherwise would only flatter the team.

Tickets are the opposite kind of thing. They are for the people doing the work, they are meant to finish, and they are disposable. A story is never “done” in that sense. It is fulfilled, and then true.

One slice at a time #

Work happens in slices, which Barnspec calls Phases. There is the one being built and the ones already released. There is no backlog and no pile of parked or far-ahead Phases, because only the next slice is understood well enough to plan. When the slice is proven, release it and plan the next from what was learned.

Releasing is the one lock point. Until then everything in the Phase can be reworded, restaged or deleted, because the first wording is rarely the right one. After it, what was released stays exactly as it was, so a later change can never be contradicted by someone quietly editing what it changes. Barnspec lists what a release will lock before you agree to it, and refuses to release a Phase that is not proven.

A released story changes only by elaboration #

A released story’s record can still turn out wrong or thin: a case was missing, or the business changed its mind. That is a change to what the record says, and it deserves the same care as the record. So once a Phase is released, its stories stop changing directly. A change is made by elaborating the story in the Phase being worked on now, adding, amending or retiring Scenarios, and it is planned and proven like any other work.

Nothing is thrown away. The elaboration keeps what the story said before, so the record can always show how it came to read the way it does.

A bug is a flaw in the record #

When something was assumed to work and doesn’t, the code usually did what the record asked, and the record asked for the wrong thing. A bug ticket sitting beside the specification holds that knowledge somewhere that gets thrown away once the fix ships. So the fix starts in the specification: the story is elaborated, the missing case added or the wrong one amended, and the work then makes it true.

A regression is different. There the record was right and a released Scenario that used to pass has stopped passing. Nothing needs elaborating. The run fails, and the fix is making it pass again.

The reward is a promise; its impact is what happened #

Scenarios prove that a role can do what it wanted. Nothing in the code can show that doing it gave them somewhere to stay, or stopped them phoning the front desk. A story’s impact records that, per Phase the story shipped in, as a dated, attributed, one-sentence observation: evaluating, achieved, none or superseded.

Barnspec asks about earlier Phases’ rewards when a Phase is released, but never refuses to release because one is unanswered. A sign-off that has to be given gets given. An unanswered reward stays visibly unanswered instead.

Impact never changes a story’s colour. A story can be green and have delivered no value, two true facts side by side. If admitting “none” cost the team its green, nobody would admit it. And only the role, or someone speaking for them, can settle “achieved”, because a team cannot close a claim about someone else’s experience.

What it refuses to be #

  • A backlog, an estimate or a ceremony. There is one Phase to build and nothing to size.
  • A place to sign work off by hand. Evidence turns a Scenario green and nothing else does.
  • A record tied to one codebase or technology. Stories describe needs, so they outlive the code.
  • A tool that guesses. Where it cannot be sure, it asks.
